SECTION 8 — REQUIREMENTS
==================================================

Risk Manager is the account-protection layer between AI Decision Engine and Trade Manager.

Required workflow:

AI Decision Engine
        ↓
Risk Manager
        ↓
Trade Manager

Trade Manager must not execute a trade unless Risk Manager has approved it.

--------------------------------------------------
8.1 RISK PER TRADE
--------------------------------------------------

Implement configurable maximum risk per trade.

Examples:
- 0.5%
- 1%
- 2%

Requirements:
- Risk percentage must come from configuration/user settings.
- Requested risk must never exceed configured maximum.
- Invalid/negative/zero risk values must be rejected.
- Calculate actual monetary risk from account equity/balance as appropriate.
- Use MT5/Exness symbol/account information, not fake/demo market data.

--------------------------------------------------
8.2 AUTOMATIC LOT SIZE
--------------------------------------------------

Implement production-safe lot sizing using:

- Account balance/equity
- Risk %
- Entry price
- Stop Loss
- Stop-loss distance
- Tick size
- Tick value
- Contract/symbol specifications
- Minimum volume
- Maximum volume
- Volume step

The calculation must work with actual MT5 symbol specifications.

Requirements:
- Correctly normalize lot size to broker volume step.
- Respect min/max volume.
- Never return negative, zero, NaN, or infinite volume.
- Do not exceed configured monetary risk after normalization.
- Handle invalid/missing symbol specifications safely.
- Avoid hardcoded pip values where MT5 tick specifications provide the correct data.

--------------------------------------------------
8.3 STOP LOSS VALIDATION
--------------------------------------------------

Validate AI/SMC-provided SL before approval.

Checks should include where data is available:

- SL exists
- SL is on the correct side of entry
- SL is not zero/invalid
- Minimum SL distance
- Maximum SL distance
- Current market price relationship
- Market structure
- Order Block relationship
- Liquidity relationship

Do not invent SMC data.
If SMC context is unavailable, use the existing interfaces/state and mark that validation as unavailable rather than fabricating approval.

--------------------------------------------------
8.4 TAKE PROFIT VALIDATION
--------------------------------------------------

Validate TP.

Checks:
- TP exists
- TP is on the correct side of entry
- TP is valid relative to entry
- Market structure where available
- Liquidity target where available
- Supply/Demand where available
- RR calculation

Do not invent liquidity or SMC levels.

--------------------------------------------------
8.5 RISK / REWARD
--------------------------------------------------

Implement configurable minimum RR.

Examples:
- 1:2
- 1:2.5
- 1:3

Calculate RR from actual entry, SL and TP.

Reject trade when:

RR < configured minimum.

Handle invalid distances safely.

--------------------------------------------------
8.6 MAXIMUM OPEN TRADES
--------------------------------------------------

Implement configurable maximum open trades.

Before approval:
- Read actual currently open positions/orders from MT5/Trade Manager infrastructure.
- Reject new trade when configured limit is reached.

Do not count fake/demo positions.

--------------------------------------------------
8.7 MAXIMUM DAILY LOSS
--------------------------------------------------

Implement configurable daily-loss protection.

Track the trading day's realized loss and relevant floating loss according to the existing account/trade architecture.

When configured daily loss limit is reached:
- Block new trades.
- Existing trades are NOT automatically closed unless existing architecture explicitly requires it.
- Keep protection active until the next trading day.

Daily reset must be deterministic and timezone-aware.

Do not rely only on process memory if the project already has persistent account/trade state available.

--------------------------------------------------
8.8 MAXIMUM DAILY PROFIT
--------------------------------------------------

Implement optional configurable daily-profit protection.

If enabled and target is reached:
- Block new trades.

Existing trades remain untouched unless another protection rule requires action.

--------------------------------------------------
8.9 DRAWDOWN PROTECTION
--------------------------------------------------

Monitor:
- Current drawdown
- Floating drawdown
- Maximum drawdown

Use actual account equity/balance.

If configured drawdown limit is exceeded:
- Block new trades.
- Produce a clear protection/rejection reason.
- Expose protection state for dashboard/API if existing architecture supports it.

Do not silently approve trades while protection is active.

--------------------------------------------------
8.10 CONSECUTIVE LOSS PROTECTION
--------------------------------------------------

Implement configurable consecutive-loss limit.

When the limit is reached:
- Block new trades.
- Track/reset correctly after a winning/qualifying trade according to the existing trade history model.
- Avoid counting the same closed trade more than once.

If there is no suitable persistence currently available, implement a clean persistence-compatible state mechanism rather than an uncontrolled global variable.

- Handle missing/invalid tick data safely.

Do not use external market-data providers.

Do not hardcode behavior that conflicts with configurable settings.
