# SECTION 8 REQUIREMENTS

Implement/complete these requirements:

### 8.1 Purpose

Risk Manager must:

* calculate risk
* calculate lot size
* validate SL
* validate TP
* validate Risk/Reward
* monitor daily loss
* prevent overtrading

### 8.2 Workflow

AI Decision Engine
→ Risk Manager
→ Trade Manager

No trade may reach broker execution without Risk Manager approval.

### 8.3 Risk Per Trade

Respect configured user risk percentage.

Examples:

* 0.5%
* 1%
* 2%

Never approve risk above the configured maximum.

### 8.4 Automatic Lot Size

Calculate lot size using:

* account balance/equity
* configured risk %
* SL distance
* pip/tick value
* symbol specifications
* broker volume min/max/step

Normalize the result to broker-supported volume constraints.

Never exceed the calculated monetary risk budget.

### 8.5 Stop Loss Validation

Validate:

* correct direction
* SL is actually on the protective side of entry
* SL distance is valid
* maximum SL distance if configured
* reject invalid/missing SL

Where Section 8 architecture has reliable SMC/structure information available, validate structural placement without inventing unavailable data.

### 8.6 Take Profit Validation

Validate:

* TP is on the correct side of entry
* TP is valid for direction
* TP produces acceptable reward
* reject invalid/missing TP

Use available structure/liquidity information only if it already exists and can be consumed safely.

### 8.7 Risk/Reward

Calculate:

reward / risk

Reject if below configured minimum.

Default minimum may remain the existing project value if already implemented.

Handle floating-point boundary safely.

### 8.8 Maximum Open Trades

Respect configured maximum open trades.

If the limit is reached:
→ reject new trade.

### 8.9 Maximum Daily Loss

Track daily loss.

When configured daily loss limit is reached:
→ reject new trades.

Existing positions may continue to be monitored.

Daily statistics must reset correctly at the start of a new trading day.

### 8.10 Maximum Daily Profit

If configured/enabled:
→ stop approving new trades after the target is reached.

If disabled:
→ do not block trading.

### 8.11 Drawdown Protection

Monitor:

* current drawdown
* configured maximum drawdown

If limit is crossed:
→ trading paused/rejected.

### 8.12 Consecutive Loss Protection

Track consecutive losing trades.

If configured limit is reached:
→ reject new trades until protection resets according to the existing design.

### 8.13 Spread Protection

Read current spread from the broker/data layer.

If spread exceeds configured maximum:
→ reject trade.

### 8.14 Session Protection

Use the project's existing session utility if available.

If allowed sessions are configured:
→ approve only during allowed sessions.

If no sessions are configured:
→ all sessions remain allowed.

### 8.15 News Protection

Use the existing News Filter interface.

If high-impact news blocks trading:
→ reject trade.

If news status cannot safely be determined and the architecture defines fail-closed behaviour:
→ reject trade.

Do not invent a news provider here if the real provider belongs to a later section.

### 8.16 Correlation Protection

**Future scope.**

Do not implement fake correlation logic.

Keep the architecture extensible for future correlation controls.

### 8.17 Exposure Control

Monitor:

* total open exposure
* currency exposure
* relevant account exposure limits

Reject trades exceeding configured limits.

### 8.18 Final Trade Validation

Before approval, verify all applicable checks:

* AI approval/input valid
* confidence requirements if already supplied by upstream
* SMC requirements if already supplied by upstream
* risk %
* lot size
* SL
* TP
* RR
* spread
* session
* news
* maximum open trades
* daily loss
* daily profit if enabled
* drawdown
* consecutive losses
* exposure

If any required check fails:

**REJECT TRADE.**

### 8.19 Dashboard/API Output

Expose the existing Risk Manager state/approval information through the project's established API conventions.

At minimum, support:

* risk %
* lot size
* RR
* SL
* TP
* expected loss
* expected profit
* daily risk used
* daily loss
* drawdown
* protection state

Use the project's existing camelCase API serialization convention.

### 8.20 Trade Manager Security Boundary

This is mandatory.

`TradeManager.open_trade()` must reject execution when:

* no RiskApproval is supplied
* approval is rejected
* approval is expired/invalid if expiry exists
* symbol differs
* direction differs
* entry differs
* SL differs
* TP differs
* lot size differs

The approval must be bound to the exact approved order parameters so a caller cannot obtain approval for one trade and execute another.
