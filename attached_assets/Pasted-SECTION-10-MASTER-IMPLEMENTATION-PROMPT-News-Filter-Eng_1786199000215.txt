10.1 RESPONSIBILITY

Create a production-ready News Filter Engine responsible for:

detecting economic events,
classifying impact,
identifying affected currencies,
identifying affected forex pairs,
determining whether a pair is inside a configurable news-risk window,
informing the Risk Manager,
exposing news information through the API/dashboard layer,
generating pause/resume state,
maintaining upcoming/live/finished event state.

The News Filter must not independently execute trades or make trading decisions.

Architecture:

Economic Calendar Provider
          ↓
   News Filter Engine
          ↓
      Risk Manager
          ↓
     Trade Manager
10.2 PROVIDER ARCHITECTURE

Create a provider abstraction such as:

EconomicCalendarProvider

with operations needed to retrieve upcoming/relevant economic events.

The provider must return normalized internal news-event objects.

Do not hardcode a fake external API.

If the project already contains a news provider, reuse it.

If no real provider exists:

create the provider interface,
create a safe unavailable/no-data implementation,
make the News Filter operate correctly when no provider is configured,
never fabricate economic events,
never generate fake news timestamps,
never pretend live news data is available.

Provider failures must be handled gracefully.

10.3 NEWS EVENT MODEL

Create or extend the appropriate database/domain model according to existing architecture.

A normalized news event should contain at minimum:

event_time

LIVE

Do not store credentials or provider secrets inside news records.

10.4 IMPACT CLASSIFICATION

Support:

HIGH

Examples:

Interest Rate Decision
FOMC
NFP
CPI
GDP
Central Bank Speech
MEDIUM

Examples:

Manufacturing PMI
Retail Sales
Employment Reports
LOW

Normally ignored for trading-risk purposes unless the user enables them.

Do not rely only on event-name string matching if the provider already supplies an impact level.

Provider-supplied impact should be normalized into the internal enum.

10.5 CURRENCY DETECTION

The engine must determine which currency is affected by each event.

Example:

USD → USD-related events
JPY → JPY-related events
EUR → EUR-related events
GBP → GBP-related events
AUD → AUD-related events
NZD → NZD-related events
CAD → CAD-related events
CHF → CHF-related events

Create a centralized currency-to-pair mapping based on the project's supported FOREX_PAIRS.

Do not hardcode a separate incompatible pair list.

For example:

USD news:
EURUSD
GBPUSD
USDJPY
USDCHF
USDCAD
AUDUSD
NZDUSD

JPY:

USDJPY
EURJPY
GBPJPY

The actual affected-pair calculation must be deterministic and based on the pair's base/quote currencies.

10.6 PAIR IMPACT DETECTION

Provide functionality such as:

get_affected_pairs(event)

and/or:

is_pair_affected(pair, event)

A pair is affected when its base or quote currency matches the event currency.

Example:

USD event + EURUSD → affected
USD event + GBPUSD → affected
USD event + EURGBP → not affected

Avoid duplicate pair results.

10.7 NEWS RISK WINDOW

Implement configurable windows.

Required configuration:

NEWS_HIGH_IMPACT_ENABLED
NEWS_MEDIUM_IMPACT_ENABLED
NEWS_LOW_IMPACT_ENABLED

NEWS_PAUSE_BEFORE_MINUTES
NEWS_RESUME_AFTER_MINUTES

Default values may follow the specification:

before = 30 minutes
after = 15–30 minutes

But use the project's existing configuration conventions.

Do not hardcode these values in business logic.

10.8 NEWS STATE

For each event determine:

UPCOMING

Current time is before the event.

LIVE

Current time is within the event's active/news period.

FINISHED

The event and its configured post-news window have ended.

Use timezone-aware UTC internally.

Do not mix naive and timezone-aware datetimes.

10.9 PAIR TRADING STATUS

Expose a deterministic evaluation function such as:

evaluate_pair(pair, now)

It should return information such as:

pair
affected
blocked
reason
impact
event_name
event_time
minutes_to_event
status

Possible reasons:

NO_RELEVANT_NEWS
HIGH_IMPACT_NEWS_WINDOW
MEDIUM_IMPACT_NEWS_WINDOW
LOW_IMPACT_NEWS_WINDOW
NEWS_PROVIDER_UNAVAILABLE

Do not silently convert provider failure into fake "safe" news status.

The system should distinguish:

NO NEWS

from:

NEWS DATA UNAVAILABLE
10.10 RISK MANAGER INTEGRATION

The News Filter must provide information to the existing Risk Manager.

Do not bypass the Risk Manager.

Do not create a second risk engine.

Extend the existing Risk Manager integration using the project's existing architecture.

The Risk Manager should be able to determine:

news_blocked = True/False

and the reason.

Example:

Risk Manager
    ↓
News Filter
    ↓
HIGH_IMPACT_NEWS_WINDOW
    ↓
Risk approval rejected

The News Filter itself must not create the final BUY/SELL/NO-TRADE decision.

10.11 TRADE MANAGER BOUNDARY

10.12 EXISTING OPEN TRADES

V1 must NOT automatically close existing trades merely because news is approaching.

Support configurable policy/state information for:

MANUAL_MONITORING

If the existing architecture already supports break-even or SL adjustment through approved paths, do not bypass those paths.

Do not implement automatic SL tightening or break-even movement unless explicitly supported by the existing specification and architecture.

10.14 COUNTDOWN

Dashboard/API should provide a calculated countdown:

minutes_to_event

or equivalent.

Calculate it dynamically from the current UTC time rather than storing a constantly changing countdown in the database.

For finished events it may be:

null

or another clearly documented representation.

10.15 ALERTS

Implement the domain/event mechanism needed for:

HIGH_IMPACT_NEWS_COMING
TRADING_PAUSED
TRADING_RESUMED

Follow the project's existing notification/event architecture.

Do not invent a completely separate notification framework if one already exists.

Alerts should be generated based on state transitions, not every polling cycle.

Example:

UPCOMING
   ↓
pause window reached
   ↓
TRADING_PAUSED

and later:

post-news window finished
   ↓
TRADING_RESUMED

Avoid duplicate alerts.

10.16 BACKGROUND REFRESH

If the project already has a background-task pattern, use it.

News refresh should:

periodically request provider data,
normalize events,
update/cache relevant events,
handle provider failures,
avoid duplicate events,
not crash the application,
stop cleanly during application shutdown.

Do not create multiple background loops.

Use configuration for refresh interval.

10.17 CACHING

Do not call an external provider unnecessarily on every Risk Manager evaluation.

Implement an appropriate cache/database strategy.

Risk evaluation should preferably operate against normalized locally available data.

Cache/provider failures must be distinguishable from genuinely having no relevant events.

10.18 DUPLICATE EVENTS

Normalize provider events using a stable identity.

Avoid creating duplicate database records every time the provider refreshes.

Possible identity components:

provider
event_name
currency
event_time

Use a proper unique constraint where appropriate.

Do not rely only on Python in-memory duplicate checking.

10.20 SECURITY

The News Filter must:

never expose provider API keys,
never log provider secrets,
never return secrets through API responses,
validate provider data,
sanitize external strings where appropriate,
use timezone-aware timestamps,
avoid arbitrary URL fetching based on untrusted user input,
avoid executing provider-provided content.
